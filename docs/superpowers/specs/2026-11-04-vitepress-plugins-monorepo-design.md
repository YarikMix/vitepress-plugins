# Личный монорепозиторий VitePress-плагинов

Дата: 2026-11-04. Статус: утверждён пользователем 2026-11-04, включая bootstrap и первый рабочий выпуск.

Это отдельный проект: новый публичный репозиторий, три npm-пакета, их выпуск и подключение к docs. Сейчас в локальной папке будущего репозитория записана только эта спека; первый коммит документа будет сделан после утверждения, вместе с созданием репозитория. Продуктовые файлы и удалённые ресурсы на этапе дизайна не создаются.

## Зачем

Собрать принадлежащие пользователю VitePress-плагины в `YarikMix/vitepress-plugins`, выпускать их по версиям в npm под аккаунтом `wely6743` и использовать опубликованные пакеты в `Cringe-Driven-Development-Team/docs`. Обслуживать код и выпуск в одном месте, сохраняя отдельные обязанности пакетов.

## Согласованные решения

- Создаётся новый репозиторий `YarikMix/vitepress-plugins`.
- Из `TP-Prepare/frontend-packages` берётся только `vitepress-module-graph`; исходная репа целиком не переносится.
- В первый этап входят module-graph, форк Mermaid renderer, общий просмотрщик Mermaid/Eraser и переключение docs на все три пакета.
- Все три пакета публичные, npm-scope — `@wely6743`.
- Выпуски автоматизируются release-please. Пакеты имеют независимые версии.

## Рассмотренные подходы

1. Перенести весь `TP-Prepare/frontend-packages` со сменой владельца и имени. Сохраняет готовую инфраструктуру и историю, но переносит также example-пакеты и весь репозиторий организации. Пользователь отклонил.
2. Создать новую личную репу и перенести только нужный пакет module-graph, затем добавить renderer и viewer. Требует перенастроить выпуск и зафиксировать происхождение исходников, зато состав соответствует личному набору плагинов. Пользователь выбрал этот подход.
3. Оставить отдельные репозитории и повторять workflow публикации. Меньше действий с форком, но не достигает цели общего места разработки и выпуска; не выбран.

Перед реализацией источники и актуальный `docs/main` проверяются заново. Новые изменения не откатываются к описанным исходным SHA; при пересечении с этим дизайном различия сначала разбираются.

## Состав репозитория

```text
packages/
  vitepress-module-graph/
  vitepress-mermaid-renderer/
  vitepress-diagram-viewer/
scripts/                       проверки архивов и публикация
tests/site/                    один небольшой совместный VitePress-стенд
docs/                          подключение, выпуск, обновление исходников
release-please-config.json
.release-please-manifest.json
```

Корень — private Bun workspace, без публикуемого общего пакета. Переносятся необходимые исходники, тесты, сборка и документация, а не зависимости и готовый `dist`. В `ORIGINS.md` фиксируются исходные репозитории, пути и SHA; исходные лицензии и авторство сохраняются. Истории целых репозиториев не импортируются. Исходные репы и их npm-публикации не удаляются и не переименовываются.

Не вводим общий framework, Nx/Turborepo, отдельный пакет core или новый универсальный интерфейс адаптеров. Сохраняем существующие сборочные подходы и тесты; root-команды только запускают проверки пакетов. Vitest форка не переписывается на Bun test ради унификации.

## 1. `@wely6743/vitepress-module-graph`

Переносится весь существующий пакет: модель, загрузчик VitePress, тема и CSS, граф/архив/шапка трека, CLI проверки модулей и работы со снимком GitHub-доски. Сохраняются экспорты и имя бинарника `module-graph`; меняются npm-имя, внутренние ссылки на него, repository/bugs и инструкции подключения.

Модель данных, frontmatter, GitHub Projects и внешний вид не пересматриваются. Тестовые данные пакета отделяются от конкретных данных CDD; тесты, входящие в исходный пакет, сохраняются. Нужные скрипты проверки npm-архива переносятся без example-core/example-addon.

## 2. `@wely6743/vitepress-mermaid-renderer`

Переносится текущий личный форк, а не исходный upstream без наших исправлений. Сохраняются `createMermaidRenderer`, `MermaidRenderer`, типы настроек, `/css`, static-режим, темы и существующие функции встроенного интерфейса форка.

В docs renderer используется с `static: true`: он отвечает за SVG и события результата, внешний viewer — за масштабирование и панель. Зависимость на viewer в renderer не появляется. Обновляются npm-имя, самоссылки, package metadata и тестовые импорты; source upstream и его лицензия явно указаны.

Существующий `YarikMix/vitepress-mermaid-renderer` сохраняется как отдельный источник истории/сравнения с upstream, но docs больше не зависит от его Git SHA. Автоматическая синхронизация двух реп не создаётся. Новые изменения делаются в монорепозитории; обновление upstream описывается короткой инструкцией сравнения с SHA из `ORIGINS.md`.

## 3. `@wely6743/vitepress-diagram-viewer`

Переносится проверенное поведение общего просмотрщика, без редизайна:

- обычное колесо прокручивает страницу; Ctrl/⌘ + колесо масштабирует схему;
- кнопки уменьшения/увеличения, вписывание по обеим сторонам, уменьшение ниже начального масштаба;
- перетаскивание, стрелки в фокусе, fullscreen и существующий overlay при недоступности Fullscreen API;
- читаемый начальный размер и ограничение высоты рамки 70vh;
- восстановление фокуса/прокрутки после fullscreen, очистка обработчиков и защита асинхронных операций;
- пары «текст + схема», их адаптивный перенос и выравнивание `#` у первого заголовка.

Публичные экспорты корня:

| Экспорт | Контракт |
| --- | --- |
| `DiagramFrame` | существующие `title`, `size: {width, height} \| null`; слоты default/status/footer |
| `MermaidFrame` | существующий необязательный title и default slot с Mermaid-разметкой; обработка результата renderer и размера SVG |
| `EraserFrame` | title, src, size и необязательный pngSrc; iframe с существующими sandbox/lazy/shield, состояние отсутствия схемы и footer/status slots |
| `DiagramSection` | существующие default и diagram slots |
| `DiagramSize` | тип ширины и высоты натурального холста |

`/style.css` содержит только CSS просмотрщика и DiagramSection, включая нужные правила Mermaid SVG/подписей. `/node` экспортирует перенесённый Markdown-плагин `mermaidFence`; он не импортирует браузерные компоненты при Node/SSR-загрузке.

`DiagramFrame` и `MermaidFrame` сохраняют рабочие DOM-классы, атрибуты, события и признак готовности холста, на которые сейчас опираются loader и браузерные проверки docs. Новый протокол готовности в рамках переноса не придумывается.

Vue и целевая версия VitePress остаются peer dependencies; Panzoom — runtime dependency viewer. Renderer не включается в viewer: Eraser-компонент должен использоваться без установки Mermaid. README показывает совместное подключение renderer и MermaidFrame через существующий event-контракт. Новых runtime-зависимостей между тремя пакетами не требуется.

## Что остаётся в docs

- `diagrams.data.ts`, список имён схем, чтение PNG и вычисление путей HTML/PNG.
- Тонкий `Diagram.vue`: разрешает name в URL/размер и вызывает пакетный `EraserFrame`, сохраняя текущую команду рендера в сообщении об отсутствующей схеме.
- Лоадер статьи, Nolebase-настройки ширины, управление якорями, копирование ссылок, Figma и особенности темы сайта.
- Генерация Eraser HTML/PNG, normalisation корневого HTML и сборка страниц/превью. Это не обязанности браузерного viewer.

Локальные копии перенесённых компонентов, CSS и функций удаляются из docs после проверки пакетной замены. Специфические тесты страницы остаются в docs, тесты математики и компонентов переезжают вместе с кодом; одинаковые unit-тесты в двух репах не размножаются.

## Выпуск

Мой предлагаемый выбор: первый рабочий выпуск всех трёх новых имён — `0.1.0`. Затем версии и CHANGELOG ведёт release-please отдельно для каждого package path. Один общий manifest release PR может включать несколько пакетов; у каждого свой tag и GitHub Release. Общей синхронной версии всего репозитория нет.

Workflow `.github/workflows/release.yml`:

1. На main release-please готовит/обновляет release PR по Conventional Commits.
2. CI проверяет release PR так же, как обычный PR. Проверяется реальная работа CI на созданном ботом PR; при необходимости настройки токена выбираются по правилам GitHub, а не предполагаются рабочими.
3. После слияния release PR создаются теги/релизы, собираются и проверяются архивы точного release commit.
4. Публикуются только пути, для которых создан релиз. Список валидируется до первой записи в registry. Сборка и упаковка проходят до публикации всех выбранных пакетов; при ошибке workflow завершается с ошибкой.
5. Публикация идёт настоящим npm CLI через OIDC на GitHub-hosted runner. Node/npm выбираются из поддерживаемых актуальных версий; проверенные минимумы npm — 11.5.1 и Node — 22.14.0. `repository.url` у каждого пакета указывает на `YarikMix/vitepress-plugins`, `directory` — на его package path.

### Первичная регистрация и подтверждение OIDC

Мой предлагаемый выбор для bootstrap: сначала подготовить и проверить три архива версии `0.0.0`, опубликовать их из авторизованного npm-аккаунта `wely6743` с dist-tag `bootstrap`. Это регистрирует имена и даёт доступ к package settings; рабочие потребители эту версию не используют. Затем настроить Trusted Publisher каждого пакета на `YarikMix/vitepress-plugins`, `release.yml`, с разрешением прямого `npm publish`. После этого release-please выпускает первые рабочие `0.1.0`, а workflow публикует их через OIDC. Так работа автоматической публикации доказана для всех трёх пакетов, а не только нарисована конфигурацией.

Перед любым bootstrap publish проверяются npm-аккаунт, содержимое tarball, имена/версии, public access и отсутствие версии в registry. Вход/2FA выполняется штатным npm login; пароли, OTP и токены не запрашиваются текстом в чате. Долгоживущий npm-токен в репозитории не хранится. Если настройка в npm требует участия владельца, запрашивается конкретное действие после подготовки проверяемого результата.

Runbook описывает восстановление частичного выпуска: успешно опубликованную версию нельзя перезаписать; проверяется registry и исходный release commit, допубликовываются только отсутствующие версии из проверенных артефактов. Повторный запуск не должен слепо пропускать несовпадающие уже существующие артефакты или выпускать все пакеты заново. Конкретный минимальный способ восстановления оставлен исполнителю.

## Переключение docs

После успешного npm-выпуска docs устанавливает обычные точные версии `0.1.0` трёх пакетов и обновляет lockfile. Git-зависимость renderer и старое имя module-graph удаляются.

Обновляются все импорты package paths в theme/config/data loaders, CSS, `ssr.noExternal` для поставляемых Vue-файлов, подключение `mermaidFence`, проверки, CLI/workflow-ссылки и инструкции. Публичные глобальные имена компонентов и Markdown страниц сохраняются. Конкретные схемы, данные модулей, IDs страниц и якоря не переписываются.

Два независимых результата: новые npm-пакеты и отдельный PR в docs. У docs до завершения этого PR остаётся работающая текущая конфигурация; параллельный legacy-режим или одновременная поддержка старых пакетов не вводятся. Переключение считается завершённым после проверки реального Pages-превью с опубликованными npm-версиями.

## Проверка и приёмка

- Каждый пакет собирается и проверяется своими настоящими тестами. Новые проверки нужны для изменённых границ: упаковка, exports, новый EraserFrame, зависимости, выбор пакетов для выпуска; не для текстового сравнения скопированного кода.
- Три npm-архива устанавливаются вне монорепозитория. Из них строится небольшой совместный VitePress-стенд на `2.0.0-alpha.21`: модульный граф, Markdown Mermaid и Eraser HTML. Проверяются exports, CLI, типы, CSS, SSR/build и dev-загрузка, чтобы workspace не скрывал отсутствующие файлы.
- Сохраняются существующие тесты форка. Интеграция с docs проверяет используемый Mermaid 11 и VitePress 2; поддержка других версий не расширяется в ходе переноса. Если исходный форк заявляет Mermaid 12, его существующая проверка на Mermaid 12 тоже сохраняется.
- Просмотрщик: читаемый старт, обычное колесо страницы, Ctrl/⌘-zoom, достижимость уменьшения/полного fit, resize, drag/стрелки, fullscreen/overlay/Escape, фокус и cleanup; оба вида схем, обе темы, широкий/узкий экран и root/nested base. Семантически те же регрессии переносим/используем из docs.
- В docs проходят typecheck, modules check, tests, полный build/site check. Проверяются loader/anchor navigation и новый пакетный viewer на root и nested base; module-graph сохраняет данные, sidebar, шапки и CLI. Нет повторной панели Mermaid и внутренних скроллов Eraser.
- На npm опубликованы все три `0.1.0`, версии устанавливаются по registry, repository metadata верна. Все три рабочего выпуска выполнены успешным OIDC workflow, а независимый последующий релиз не требует выпускать неизменившиеся пакеты.
- У PR в docs зелёный CI и настоящее опубликованное Pages-превью; в нём проверены graph, Mermaid/Eraser и отсутствие ошибок браузера. Факт появления release PR, GitHub Release или dispatch Pages сам по себе не считается доказательством npm-публикации/выкладки.

## Границы

Не переносим example-пакеты, весь сайт docs или инструменты рендера Eraser в npm-viewer. Не добавляем новые возможности схем, редизайн, общий мегаплагин, новые схемы конфигурации, переводы интерфейса, поддержку старых API/клиентов, автоматическое обновление upstream и дополнительные системы сборки.

## Решения, оставленные исполнителю

Размещение внутренних файлов/фикстур и выбор минимальных root-команд; точные настройки сохранённых сборщиков; минимальный механизм восстановления частичной публикации; организация PR в новом репозитории. Все выбранные способы обязаны подтверждать описанную приёмку настоящими npm-архивами и опубликованным docs-превью.

Мои предложения, требующие проверки при утверждении дизайна: первые рабочие версии `0.1.0`; регистрация через `0.0.0`/tag `bootstrap`; сохранение исходных репозиториев; отсутствие импорта всей истории и дополнительных runtime-связей между пакетами; сохранение loader/якорей/поиска Eraser-файлов в docs.
